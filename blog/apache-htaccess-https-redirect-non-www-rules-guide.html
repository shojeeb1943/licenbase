Apache .htaccess HTTPS Redirect & Non-WWW Rules Generator Guide

By LicenBase Team Published November 12, 2026 4 min read

Every modern website must enforce sitewide HTTPS encryption and establish a single canonical domain format. When users type your domain into a browser, search engines evaluate four distinct URL variations. If you fail to redirect non-secure HTTP and www subdomains to your preferred apex canonical URL, your search ranking signals divide, and visitors encounter security warnings. This technical guide provides foolproof mod_rewrite rules alongside our interactive .htaccess Rewrite Rule Generator.

1. The Canonical Redirection Problem

Search engines treat each protocol and subdomain combination as a separate website entity:

  • http://example.com (Unencrypted Apex)
  • http://www.example.com (Unencrypted Subdomain)
  • https://www.example.com (Encrypted Subdomain)
  • https://example.com (Preferred Canonical Target)

To eliminate duplicate content indexing and consolidate 100% of your inbound backlink authority into your primary address, configure a unified 301 Permanent Redirect inside your root .htaccess file.

2. The Unified Single-Redirect Code Snippet (Best Practice)

Many webmasters make the mistake of chaining two separate redirects: first redirecting HTTP to HTTPS, and then redirecting WWW to non-WWW. Chained redirects cause two round-trip network hops, inflating TTFB and degrading Core Web Vitals.

Use this unified Apache/LiteSpeed rewrite block that resolves both conditions in a single 301 redirect:

<IfModule mod_rewrite.c>
RewriteEngine On
RewriteBase /

# Force HTTPS and Non-WWW in a single request
RewriteCond %{HTTPS} off [OR]
RewriteCond %{HTTP_HOST} ^www\.(.+) [NC]
RewriteRule ^(.*)$ https://%1/$1 [R=301,L]
</IfModule>

If you prefer using www.example.com as your canonical brand format, simply reverse the host check:

# Alternative: Force HTTPS and WWW
RewriteCond %{HTTPS} off [OR]
RewriteCond %{HTTP_HOST} !^www\. [NC]
RewriteRule ^(.*)$ https://www.%{HTTP_HOST}/$1 [R=301,L]

3. Cloudflare & Reverse Proxy Flexible SSL Compatibility

If your domain operates behind Cloudflare, an AWS Application Load Balancer, or an Nginx reverse proxy terminating SSL at the edge, the server variable %{HTTPS} may register as off even when the visitor is on HTTPS. Use the forwarded protocol header instead:

RewriteCond %{HTTP:X-Forwarded-Proto} !https
RewriteCond %{HTTPS} off
RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]

This prevents the dreaded ERR_TOO_MANY_REDIRECTS browser loop.

4. HSTS: Hardening Browser Security at the Header Level

After validating that your 301 redirects function cleanly, instruct browsers never to load your site over insecure HTTP again using HTTP Strict Transport Security (HSTS):

<IfModule mod_headers.c>
Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
</IfModule>

HSTS stops man-in-the-middle SSL stripping attacks before the browser even transmits the initial HTTP request.

5. Command-Line Verification with cURL

Before testing in desktop browsers that aggressively cache 301 redirects, test your server header response chain directly from the terminal:

curl -IL http://example.com

Examine the returned HTTP status codes to confirm a clean single hop:

  • Step 1: Initial request returns HTTP/1.1 301 Moved Permanently with Location: https://example.com/.
  • Step 2: Follow-up request returns HTTP/2 200 OK or HTTP/3 200 OK.

If you see intermediate hops (such as HTTP pointing to WWW-HTTP, which then points to WWW-HTTPS, and finally apex HTTPS), your rewrite conditions are conflicting with CMS plugins. Consolidate them using the single unified block above.
