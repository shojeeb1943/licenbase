Check Which Process Is Using Port 80 or 443 on a Linux VPS

By LicenBase Team Published October 19, 2026 4 min read

When restarting Apache, Nginx, or LiteSpeed Web Server after a configuration update or migration, few errors are more frustrating than "(98)Address already in use: AH00072: make_sock: could not bind to address 0.0.0.0:80". In Linux networking, only one primary service can bind to a given TCP socket at any time. If an orphaned child process, a rogue Python server, or an improperly uninstalled daemon is already listening on port 80 (HTTP) or port 443 (HTTPS), your primary web server will fail to start. In this tutorial, we show you how to identify which PID is listening on port 80 or 443, terminate rogue processes safely, and restore your web services.

1. Symptoms of Socket Binding Collisions

When port 80 or 443 is blocked, systemctl outputs failure notices:

Job for httpd.service failed because the control process exited with error code.
(98)Address already in use: AH00072: make_sock: could not bind to address [::]:80
(98)Address already in use: AH00072: make_sock: could not bind to address 0.0.0.0:80
no listening sockets available, shutting down

To inspect the error journal in real time:

journalctl -xeu httpd.service

2. Inspecting Active Sockets with ss (Socket Statistics)

The modern, ultra-fast tool for inspecting network sockets on Linux is ss:

ss -tulpn | grep -E ':80\s|:443\s'

Sample terminal output:

tcp   LISTEN 0 511  0.0.0.0:80   0.0.0.0:*  users:(("nginx",pid=14812,fd=6))
tcp   LISTEN 0 511  0.0.0.0:443  0.0.0.0:*  users:(("nginx",pid=14812,fd=7))

The output reveals that an nginx daemon with PID 14812 is actively holding both ports, explaining why Apache failed to start.

3. Diagnosing with lsof and netstat

Alternatively, lsof provides detailed process mapping:

lsof -i :80 -i :443

If you prefer netstat:

netstat -tlpn | grep -E ':80|:443'

Common culprits include:

  • Dual Web Server Conflicts: Nginx reverse proxy was left running after an uninstallation, blocking Apache.
  • LiteSpeed vs Apache: LiteSpeed was activated without properly disabling Apache first.
  • Zombie Processes: A parent Apache process was killed while child worker processes remain stuck in uninterruptible sleep.
  • Custom Docker/Node/Python Containers: A containerized app was bound directly to host port 80 instead of an internal bridge port.

4. Safely Clearing Port Conflicts (fuser & kill)

To terminate the specific conflicting process gracefully by its PID:

kill 14812

If the process refuses to exit, forcefully terminate all sockets bound to ports 80 and 443:

fuser -k -n tcp 80
fuser -k -n tcp 443

5. Restarting and Verifying Web Services

Once the conflicting sockets are cleared, start your intended web server cleanly:

systemctl restart httpd

Verify that ports 80 and 443 are now properly owned by the intended service:

ss -tulpn | grep ':80'

Expected result: users:(("httpd",pid=22104,fd=4))
