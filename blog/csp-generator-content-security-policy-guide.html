CSP Generator: How to Build a Bulletproof Security Policy

By LicenBase Team Published October 17, 2026 4 min read

Cross-Site Scripting (XSS) remains one of the most widespread and damaging application-layer vulnerabilities on the web today. If an attacker discovers an unsanitized input field on your website or exploits an outdated third-party plugin, they can inject malicious JavaScript capable of stealing customer session tokens, logging credit card keystrokes, or redirecting visitors to phishing portals. Traditional firewalls and Web Application Firewalls (WAFs) offer strong perimeter defense, but modern cybersecurity requires a second line of defense operating directly inside the visitor's browser. Content Security Policy (CSP) provides that defense. In this technical walkthrough, we explain how CSP directives work, how to deploy cryptographic nonces, and how to build a production-ready policy using our free CSP generator.

1. Anatomy of Core CSP Directives

A Content Security Policy is delivered as an HTTP response header containing semicolon-separated directive instructions:

  • default-src 'self': The baseline fallback directive for any asset category not explicitly defined. Setting it to 'self' restricts resources to your exact origin.
  • script-src: Governs where JavaScript files can load from. Strict policies ban 'unsafe-inline' and require cryptographic nonces or specific CDN whitelists.
  • style-src: Controls CSS stylesheet origins and inline styles.
  • img-src and font-src: Restricts image payloads (including data URIs) and external web fonts (such as Google Fonts).
  • frame-ancestors: Restricts which parent sites can embed your pages inside an <iframe>, permanently eliminating clickjacking vulnerabilities.

2. Implementing Cryptographic Nonces in Dynamic Applications

Modern single-page applications and dynamic CMS platforms often require inline tracking tags or initialization scripts. Instead of reverting to vulnerable 'unsafe-inline', generate a unique random cryptographic nonce in your backend PHP or Node.js application:

// Backend generates random 16-byte base64 nonce
$nonce = base64_encode(random_bytes(16));
header("Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{$nonce}';");

Then embed the matching attribute into your inline script: <script nonce="<?php echo $nonce; ?>">...</script>. Browsers will execute this specific block while rejecting all injected unauthorized scripts.

Frequently asked questions

A Content Security Policy (CSP) is an HTTP response header that restricts the dynamic domains and asset sources from which browsers can load JavaScript, CSS stylesheets, images, fonts, and iframes, effectively neutralizing Cross-Site Scripting (XSS) and data injection exploits.

Allowing unsafe-inline instructs the browser to execute any inline JavaScript found inside script tags or HTML attributes (such as onclick). This completely negates the primary security benefit of CSP by allowing injected attacker payloads to execute.

A nonce is a random, cryptographically secure token generated uniquely per HTTP request (e.g., nonce-rAnd0m123) and placed on authorized script tags. A hash (e.g., sha256-abc...) is a mathematical fingerprint of static, unchanging inline script content.

Deploy the policy using the Content-Security-Policy-Report-Only header first, paired with a report-uri or report-to endpoint. Browsers will log all policy violations without blocking any legitimate website assets, allowing you to fine-tune rules safely.
