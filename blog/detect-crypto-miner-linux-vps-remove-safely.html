How to Detect a Crypto Miner on Your VPS and Remove It Safely

By LicenBase Team Published October 20, 2026 7 min read

Cryptocurrency hijacking—commonly referred to as cryptojacking—is one of the most pervasive server threats facing Linux VPS administrators today. Unlike destructive ransomware that immediately encrypts files, crypto miners (frequently variants of XMRig or custom Monero miners) are designed to remain stealthy, quietly monetizing your server's computational horsepower around the clock. When a miner takes hold, CPU load spikes to 100%, server response times crater, database queries time out, and cloud providers may suspend your instance for acceptable use policy violations. This tutorial explains how to unmask hidden mining processes, bypass user-space rootkits, safely eradicate miner persistence, and immunize your Linux VPS.

1. Common Signs Your VPS Has Been Compromised by a Crypto Miner

Attackers gain initial access by exploiting unpatched web applications (such as WordPress plugins, Log4j, or outdated Drupal modules), brute-forcing weak SSH credentials, or abusing unsecured Redis/Docker API sockets. Once inside, the symptoms manifest distinctly:

  • Sustained 100% CPU Utilization: Your hypervisor dashboard shows all virtual CPU cores pinned at maximum capacity, yet traditional terminal commands like top show normal activity.
  • Sluggish SSH Interactivity: Logging into the shell takes multiple seconds, and running simple commands incurs noticeable lag due to CPU resource starvation.
  • Hypervisor Throttling or Suspension: VPS providers issue automated warnings regarding abnormal continuous resource consumption.
  • High Outbound Network Connections to Mining Pools: Persistent outbound sockets communicating with known mining pool infrastructure across unusual ports (e.g., 3333, 5555, 14444).

2. How Modern Monero Miners Conceal Themselves from System Monitors

The primary reason sysadmins struggle to detect miners is process stealth. Advanced miner strains deploy several concealment mechanisms:

  • Shared Library Preloading: The miner modifies /etc/ld.so.preload to inject a malicious shared object library (e.g., /usr/local/lib/libprocesshider.so). This library hooks readdir() system calls, filtering out any directory in /proc that matches the miner's process ID. Consequently, top, ps, and htop simply do not see the process.
  • Binary Renaming & Masquerading: The executable is disguised with names resembling legitimate system daemons, such as [kworker/0:1H], systemd-journal, cron.d, or dbus-daemon.
  • Self-Throttling on Inspection: Some miner variants monitor whether an interactive terminal session opens (detecting tty allocation) and automatically sleep or kill their mining workers while the administrator is logged in, resuming as soon as the session disconnects.

3. Identifying the Malicious Process: Looking Past Process Hiding and Renaming

To defeat library preloading, inspect the dynamic linker configuration directly using absolute paths:

# Inspect the preload file for injected rootkit libraries
cat /etc/ld.so.preload

# If unauthorized libraries are present, neutralize immediately
> /etc/ld.so.preload

Next, use network socket analysis to track down processes communicating with external mining pools. Miners must exchange hashes with mining servers, which cannot be hidden by basic user-space rootkits:

# Scan for established outbound connections with PID mapping
ss -tupn | grep ESTAB

# Look for typical Stratum pool ports
ss -tupn | grep -E "3333|4444|5555|7777|9000|14444"

Sample output identifying the rogue process:

tcp   ESTAB  0  0  192.0.2.15:48922  198.51.100.44:3333  users:(("kworkerds",pid=14298,fd=3))

Here, the process kworkerds with PID 14298 is connected to port 3333 on an external IP. To find the physical executable location on the disk, inspect the process link in /proc:

ls -la /proc/14298/exe
cat /proc/14298/cmdline | tr '\0' ' ' ; echo ""

This reveals the real path to the malicious binary (often located in /tmp, /var/tmp, or /dev/shm) along with the wallet address and mining pool parameters.

4. Freezing and Terminating the Miner Without Triggering Watchdog Scripts

Never issue a simple kill -9 as your initial action. If a watchdog process is active, it will detect the miner's death and instantly spawn a new instance under a different PID or download a fresh binary. Instead, send the SIGSTOP signal to freeze execution:

# Freeze the process immediately (stops CPU consumption without exiting)
kill -STOP 14298

Freezing the process stops CPU exhaustion instantly while keeping the process state intact in memory, allowing you to trace its parent process tree:

# Inspect parent PID (PPID)
ps -o ppid= -p 14298

# Trace process tree using pstree
pstree -p -s 14298

If the PPID belongs to a watchdog daemon, freeze the parent process as well before terminating both:

kill -STOP <PARENT_PID>
kill -9 14298 <PARENT_PID>

Delete the binary from disk immediately and clear any immutable file attributes that the attacker may have configured:

chattr -i -a /tmp/kworkerds 2>/dev/null
rm -f /tmp/kworkerds

5. Auditing Persistence: Hidden Crons, Systemd Services, and SSH Keys

A miner will re-infect the machine within hours unless all persistence footholds are identified and purged:

  1. System and User Crontabs: Inspect both global and user-specific cron spools: 
    cat /etc/crontab
ls -la /etc/cron.*
cat /var/spool/cron/* 2>/dev/null
    Look for base64 strings or pipe commands like curl -s http://... | bash and remove them.
  2. Rogue Systemd Services and Timers: Attackers frequently drop custom service units into /etc/systemd/system/: 
    systemctl list-unit-files --state=enabled | grep -E "miner|update|system"
ls -lt /etc/systemd/system/ | head -n 15
    Inspect recently modified service files, disable them using systemctl disable --now <service>, and delete the unit files.
  3. SSH Authorized Keys: Check root and all system accounts for unauthorized public keys: 
    cat /root/.ssh/authorized_keys
cat /home/*/.ssh/authorized_keys 2>/dev/null
    Wipe unknown keys and rotate the root password immediately.

6. Hardening File Systems and Mounting /tmp with Noexec

Over 90% of crypto miners execute out of world-writable directories such as /tmp, /var/tmp, and /dev/shm. Disallowing binary execution in these partitions prevents automated drops from executing:

# Remount /tmp and /dev/shm with noexec,nosuid,nodev
mount -o remount,noexec,nosuid,nodev /tmp
mount -o remount,noexec,nosuid,nodev /dev/shm

To make these protections permanent across reboots, update /etc/fstab:

/tmp /var/tmp none bind 0 0
tmpfs /dev/shm tmpfs defaults,nodev,nosuid,noexec 0 0

Additionally, block outbound connections to known mining pool ports across your CSF or iptables firewall configuration.

Frequently asked questions

Sophisticated crypto miners utilize shared library preloading via /etc/ld.so.preload or manipulate the /proc filesystem to hook system calls. When monitoring tools like top, ps, or htop query process information, the rootkit intercepts the call and hides the miner PID and CPU consumption from display.

Miners rarely run as isolated binaries. They deploy redundant watchdog processes, infected systemd service units, and crontabs that check process status every 60 seconds. Killing the miner directly causes the watchdog to respawn it under a new PID. You must freeze the process first using `kill -STOP` while you remove the persistence mechanisms.

Miners communicate with Stratum mining pools over TCP ports such as 3333, 4444, 5555, 7777, 8080, and 9000, or use TLS/SSL encapsulation on port 443 to disguise mining hashes as normal HTTPS web traffic.

Without operating system level isolation, a miner running as an unprivileged cPanel user can scan the filesystem for world-writable directories in neighboring accounts or exploit local kernel privilege escalation vulnerabilities to gain root.

CloudLinux OS uses Lightweight Virtual Environments (LVE) to enforce strict CPU and thread quotas on each user. Even if an account executes an XMRig binary, it is throttled to its allocated CPU percentage (e.g., 25% of 1 core), preventing server-wide degradation.
