How to Fix No Space Left on Device Error on a Linux VPS

By LicenBase Team Published October 5, 2026 5 min read

Encountering the error No space left on device on a production Linux VPS can instantly halt web servers, crash database daemons, and block SSH login sessions. What makes this issue challenging is that administrators often run df -h, see available gigabytes of storage, and remain puzzled about why the operating system refuses to write new files. This comprehensive guide covers both raw storage block exhaustion and inode table exhaustion, providing actionable commands to reclaim disk space immediately.

1. Diagnosing Block Exhaustion vs Inode Exhaustion

Every file on a Linux filesystem requires two fundamental components: disk blocks to store file data and an inode entry to store file metadata (permissions, ownership, timestamps). Running out of either resource generates the exact same error message.

# Step 1: Check raw disk block capacity
df -h /

# Step 2: Check inode table capacity
df -i /

Compare the output of both commands:

  • If df -h shows 100% capacity on the root / partition, large log files, database binary logs, or backup archives are consuming disk blocks.
  • If df -i shows 100% utilization while df -h shows free gigabytes, your server has created millions of zero-byte or tiny files (such as PHP session files, email bounce queues, or image thumbnail caches).

2. Finding and Releasing Open Deleted Files (lsof +L1)

A classic sysadmin trap occurs when a massive 20GB log file is deleted using rm -f /var/log/nginx/access.log, but df -h continues reporting 100% usage. When a running process holds a file handle open, deleting the file unlinks it from the directory structure, but the disk blocks remain locked until the daemon releases the descriptor.

# Find unlinked deleted files held open by running processes
lsof +L1

# Reload the responsible service to release disk blocks (example: Nginx)
systemctl reload nginx

Never delete active log files directly with rm. Instead, truncate them in place using > /var/log/nginx/access.log or configure logrotate with copytruncate to release space without breaking active file descriptors.

3. Hunting Giant Directories and Log Hogs with ncdu

To pinpoint exactly which directories are consuming raw storage blocks, use du or the interactive ncdu visual disk analyzer:

# Find top 10 largest directories from root
du -ahx / | sort -rh | head -n 11

# Or install and launch ncdu for fast interactive scanning
dnf install -y ncdu || apt install -y ncdu
ncdu -x /

Common storage culprits include:

  • Systemd Journal Logs: Vacuum historical journal logs by running journalctl --vacuum-size=200M.
  • Package Manager Cache: Clean cached RPMs and DEB packages with dnf clean all or apt-get clean.
  • MySQL Binary Logs: Purge old binary logs inside MySQL using PURGE BINARY LOGS BEFORE NOW() - INTERVAL 3 DAY;.
  • Crash Dumps: Inspect /var/crash or /var/log/audit for accumulated core dumps.

4. Fixing Inode Exhaustion Caused by Millions of Small Files

When df -i shows 100% inode exhaustion, standard rm * commands often fail with the error Argument list too long. Use this command to count inodes across top-level directories:

# Count inodes across subdirectories in /var
find /var -maxdepth 2 -type d -exec sh -c 'echo -n "{}: " && find "{}" | wc -l' \; | sort -n -k2

Top causes of inode exhaustion and their solutions:

  • PHP Session Buildup: Clear expired session files in /var/lib/php/sessions or /tmp using find /var/lib/php/sessions -type f -cmin +1440 -delete.
  • Exim / Postfix Mail Spool: Dropped mail queues in /var/spool/exim/input or /var/spool/postfix/maildrop. Flush frozen messages.
  • CMS Cache Folders: Purge unmanaged file-based WordPress cache plugins that create millions of static HTML and CSS asset files.

5. Offloading Local Backups to Remote Cloud Storage

Storing local full cPanel backups or automated cpmove archives inside /backup or /home on a single VPS drive is one of the leading causes of sudden storage exhaustion and data corruption during backup generation.

Deploying a JetBackup license ensures disaster recovery snapshots are incrementally compressed and streamed directly to external S3, Wasabi, or Google Cloud Storage buckets. This frees up 30% to 50% of your local disk space, eliminates the risk of local disk full crashes during backups, and provides instant point-in-time file and database restore capabilities for your cPanel & WHM servers.

Frequently asked questions

Linux filesystems require both storage blocks and inode entries to write data. If your server runs out of inodes (inode exhaustion) due to millions of tiny session files or mail queue items, the system cannot create new files even if gigabytes of disk space remain.

Run df -i in your SSH terminal. Look at the Use% column. If any mount point shows 100 percent inode utilization (IUse%), your server has exhausted its inode allocation table.

When a large log file is deleted while an active process (such as Nginx, Apache, or MySQL) still holds it open, Linux unlinks the filename from the directory index but does not release the disk blocks until the holding process is restarted.

Run journalctl --vacuum-size=200M or journalctl --vacuum-time=7d to immediately purge old historical system journal logs without corrupting active systemd logging.

JetBackup automatically streams compressed incremental snapshots directly to remote S3, Wasabi, or Google Cloud Storage, removing the need to retain bulky local backup tarballs on your primary VPS disk.
