How to Fix AutoSSL Certificate Validation Failed in cPanel

By LicenBase Team Published October 19, 2026 4 min read

Free, automated SSL encryption through AutoSSL is one of cPanel's greatest operational triumphs. It completely eliminates manual certificate purchases, CSR generation, and renewal ticketing for hosting providers. However, when AutoSSL checks return "Validation Failed" or "DCV error: The certificate authority was unable to verify ownership", browsers immediately display alarming "Not Secure" warnings to site visitors. In this tutorial, we examine why AutoSSL Domain Control Validation (DCV) fails and how to fix it via terminal and WHM.

1. How Domain Control Validation (DCV) Works

Before issuing a free SSL certificate, the Certificate Authority (Let's Encrypt or Sectigo) must verify that the requesting server controls the domain. AutoSSL uses the HTTP-01 DCV Challenge:

  1. AutoSSL generates a temporary cryptographic text token inside /home/user/public_html/.well-known/pki-validation/.
  2. The CA sends an automated HTTP GET request to http://example.com/.well-known/pki-validation/TOKEN.txt.
  3. If the server returns 200 OK with the exact matching token, validation succeeds and the certificate is issued.
  4. If the request returns 403 Forbidden, 301 Redirect Loop, or times out, validation fails.

2. Fixing .htaccess Forced HTTPS Rewrite Blocks

The most common cause of failed DCV checks is a WordPress or Laravel .htaccess rule that forces all HTTP requests to HTTPS before AutoSSL has issued a valid certificate. To prevent this, add an explicit DCV exception before your rewrite rules:

RewriteEngine On
RewriteCond %{REQUEST_URI} !^/\.well-known/pki-validation/
RewriteCond %{REQUEST_URI} !^/\.well-known/acme-challenge/
RewriteCond %{HTTPS} off
RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]

This allows the CA verification crawler to access the token directly over plain HTTP port 80 without being bounced into an unencrypted redirect loop.

3. Diagnosing DNS A-Record & Proxy Conflicts (Cloudflare)

AutoSSL cannot validate domains whose DNS A records point to a different IP address, or whose traffic is proxied through an orange-clouded Cloudflare proxy with "Strict (SSL-Only)" enabled on the origin:

Verify public DNS resolution:

dig +short example.com @8.8.8.8
curl -4 ifconfig.me

If the public IP from dig does not match your server's outbound IP, the domain is pointed to an external host, and AutoSSL will fail with:

WARN The domain “example.com” resolved to an IP address “198.51.100.1” that does not refer to this server.

Instruct the client to update their DNS A record to your server's public IP address before re-running AutoSSL.

4. Triggering AutoSSL via Command Line

Instead of waiting 24 hours for the scheduled background cron job, trigger an immediate AutoSSL validation run for the specific user via SSH:

/usr/local/cpanel/bin/autossl_check --user=USERNAME

Terminal output will show real-time progress:

Checking “example.com” ...
Normalized: “example.com”
DCV status: OK
Requesting certificate from provider ...
The certificate has been installed for “example.com”!

5. Switching Provider to Let's Encrypt in WHM

If cPanel's default provider (cPanel powered by Sectigo) hits rate limits or experiences temporary maintenance, switch to Let's Encrypt:

  1. Install the official Let's Encrypt RPM via SSH: 
    /scripts/install_lets_encrypt_autossl_provider
  2. Log into WHM at https://YOUR_SERVER_IP:2087.
  3. Navigate to SSL/TLS > Manage AutoSSL.
  4. Select the Let's Encrypt radio button and click Save.
  5. Click Run AutoSSL For All Users to reissue pending certificates with wildcard SAN support.
