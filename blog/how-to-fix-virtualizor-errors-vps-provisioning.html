How to Fix Virtualizor Errors: VPS Provisioning Solutions

By LicenBase Team Published October 13, 2026 5 min read

Virtualizor is one of the most powerful, feature-rich hypervisor management panels in the hosting industry, enabling system administrators to deploy KVM, Xen, and OpenVZ/LXC virtual private servers automatically from a single master dashboard. However, when automated provisioning fails—whether due to storage volume group locks, broken Linux bridge networking, or WHMCS API synchronization timeouts—new customer orders can stall, frustrating clients and increasing tier-1 support tickets. This troubleshooting guide walks you through diagnosing and fixing the most frequent Virtualizor VPS provisioning errors.

1. Storage Pool Errors: 'Could Not Create Storage' and LVM Locks

The most common provisioning roadblock occurs when Virtualizor cannot allocate logical storage volumes for a newly requested virtual machine. Symptoms include error messages such as "Could not allocate storage" or "Storage Volume Group not found".

To diagnose and fix storage pool failures via SSH:

# 1. Inspect physical and volume group free space
vgs && pvs

# 2. Check for active volume group locks
ls -la /var/lock/lvm/
rm -f /var/lock/lvm/*

# 3. Rescan all volume groups
vgscan && vgchange -ay

# 4. Verify Virtualizor storage config in admin dashboard
# Navigate to: Storage > List Storage > Verify VG Name Matches System VG

Ensure that thin-pool metadata allocations have not exceeded 95% capacity, which can freeze QEMU/KVM disk creation.

2. Network Bridge Failures: 'Could Not Add IP to Bridge'

When Virtualizor creates a KVM guest, it binds the virtual NIC (tap interface) to a host network bridge—typically named viifbr0 or br0. If network scripts are misconfigured, provisioning aborts immediately.

To repair broken bridge networking on RHEL/AlmaLinux:

# 1. Verify bridge status and active port bindings
brctl show

# 2. Restart Virtualizor's internal networking daemon
systemctl restart virtnetwork

# 3. Verify IP Pool subnet and gateway in WHMCS / Virtualizor
# Admin Panel > IP Pool > Ensure Gateway, Netmask, and IP range match host subnet

If you are deploying on Hetzner or OVH bare-metal dedicated servers, remember that virtual MAC addresses must be assigned to each secondary IP before bridge traffic will route through the hypervisor gateway.

3. WHMCS Provisioning Timeouts and API Authentication Errors

If client orders fail to create automatically in WHMCS, check the Module Log under Utilities > Logs > Module Log. Common root causes include:

  • Firewall Port Blocking: Virtualizor communicates over ports 4084 (plain) and 4085 (SSL). Ensure your dedicated server firewall allows incoming connections on port 4085 from your WHMCS billing server IP.
  • Invalid API Credentials: In Virtualizor, navigate to Configuration > Admin ACL > API Credentials, regenerate your API Key and Secret, and update your WHMCS Server settings.
  • Incompatible Plan ID: Verify that the Plan ID specified in WHMCS module settings matches an active plan in Virtualizor.

4. VNC Console Disconnects and NoVNC WebSocket Errors

When clients click "VNC" in their client portal and receive a blank black screen or "Failed to connect to server" error, the issue is usually an unmapped SSL certificate or blocked WebSocket port:

# 1. Restart NoVNC proxy service
systemctl restart virtualizor

# 2. Ensure ports 5900 to 6000 are open in CSF / iptables
# Edit /etc/csf/csf.conf and add 5900:6000 to TCP_IN, then reload:
csf -r

5. Refreshing and Maintaining an Authorized Virtualizor License

If provisioning stalls with a "License Expired" notification in the admin header, your license status must be refreshed:

# Force license update from LicenBase automated gateway
php /usr/local/virtualizor/scripts/license.php
