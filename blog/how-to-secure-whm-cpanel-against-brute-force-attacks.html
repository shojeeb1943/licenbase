How to Secure WHM and cPanel Against Brute-Force Attacks

By LicenBase Team Published October 12, 2026 5 min read

The moment a Linux server is connected to a public IPv4 address, it becomes a target for automated credential-stuffing scanners and botnet swarms. For cPanel & WHM servers, these attacks primarily target administrative interfaces: attempting thousands of password combinations against root SSH port 22, WHM port 2087, cPanel port 2083, and mail services (Dovecot/Exim). If left unprotected, brute-force attacks not only risk catastrophic server compromise if a weak password is breached, but also waste significant CPU and memory resources processing failed authentication attempts. Securing your server requires a multi-layered defense-in-depth approach. This practical hardening guide outlines essential configuration steps to neutralize brute-force attacks on cPanel & WHM.

1. Configure cPHulk Brute Force Protection in WHM

cPanel includes a built-in application-layer security daemon called cPHulk. It monitors authentication requests across cPanel, WHM, Webmail, FTP, SSH, and mail protocols, automatically blacklisting IP addresses that exceed failed attempt thresholds.

To configure cPHulk with hardened production settings in WHM under Security Center > cPHulk Brute Force Protection:

  • IP-Based Protection: Set IP-Based Protection Period to 5 minutes, Maximum Failures per IP to 5, and Duration for IP Ban to 1 Day (or Permanent).
  • Username-Based Protection: Set Maximum Failures per Account to 10 within 30 minutes. This defends against distributed botnets that rotate through hundreds of exit IP addresses while targeting a single username.
  • Whitelist Administrator IPs: Under the Whitelist Management tab, permanently add your office and personal static IP addresses to ensure you never lock yourself out.

2. Enforce Mandatory Two-Factor Authentication (2FA)

Even if an attacker successfully guesses a password through credential stuffing, Two-Factor Authentication (2FA) renders that password useless without the dynamic Time-based One-Time Password (TOTP) from an authenticator app.

To enforce 2FA across your server:

  1. In WHM, navigate to Security Center > Two-Factor Authentication.
  2. Toggle the master status to On.
  3. Click Manage Users to configure your root account. Scan the QR code using Google Authenticator, Authy, or 1Password.
  4. Record your emergency backup codes in an encrypted password vault.

Enabling 2FA for root and reseller accounts virtually eliminates unauthorized dashboard takeovers.

3. Harden the SSH Daemon (Port & Key-Only Access)

SSH port 22 is the most heavily probed entry point on the internet. Hardening the OpenSSH daemon takes only a few minutes and permanently eliminates SSH brute-force risks:

# 1. Edit the SSH daemon configuration file
nano /etc/ssh/sshd_config

# 2. Change the default port to a high non-standard port
Port 52222

# 3. Disable unencrypted password authentication (enforce SSH keys)
PasswordAuthentication no
PubkeyAuthentication yes

# 4. Restrict direct root login to key authentication only
PermitRootLogin prohibit-password

# 5. Test configuration syntax and reload the daemon
sshd -t && systemctl restart sshd

Before closing your active SSH terminal, open a new terminal window and verify that you can connect over the new port using your private SSH key. Always update your firewall rules (CSF or firewalld) to allow incoming traffic on the new port before restarting SSH.

4. Deploy ConfigServer Security & Firewall (CSF / LFD)

While cPHulk handles application logins, CSF (ConfigServer Security & Firewall) operates at the Linux kernel packet level (iptables/nftables). Its Login Failure Daemon (LFD) monitors system logs in real time, dropping network connections from attacking IP addresses before they consume web server resources.

Install CSF via root terminal:

cd /usr/src
rm -fv csf.tgz
wget https://download.configserver.com/csf.tgz
tar -xzf csf.tgz
cd csf
sh install.sh
sh /usr/local/csf/bin/csftest.pl

Inside WHM under ConfigServer Security & Firewall > Firewall Configuration, change TESTING = "1" to TESTING = "0", ensure your custom SSH port is listed in TCP_IN, and restart the firewall.

5. Implement Automated AI Perimeter Defense with Imunify360

Modern botnets are sophisticated: they rotate through residential proxy IP addresses, execute low-and-slow login attempts to evade rate limits, and target vulnerable CMS scripts (like WordPress XML-RPC). Managing security solely through manual firewalls can quickly overwhelm administrators.

Frequently asked questions

cPHulk is cPanel's application-layer brute-force detection daemon that specifically monitors failed authentication attempts against cPanel, WHM, Webmail, SSH, FTP, and IMAP/POP3 services. Firewalls like CSF/LFD operate at the network packet level (iptables/nftables), blocking malicious IP traffic across all system ports.

In WHM, navigate to `Security Center > Two-Factor Authentication`. Enable the feature and configure user policies. Administrators and clients can then link authenticator apps (Google Authenticator, Authy, 1Password) to generate secure TOTP tokens.

Set the `IP-Based Protection` threshold to 5 failed attempts within 5 minutes, triggering a 1-day or permanent block. For `Username-Based Protection`, set the threshold to 10 failed attempts within 30 minutes to block distributed botnets targeting a single account name.

Changing your SSH port from default 22 to a non-standard high port (e.g., 2222 or 52222) eliminates over 95% of automated scripted internet scanning bots, dramatically reducing log noise and CPU overhead.
