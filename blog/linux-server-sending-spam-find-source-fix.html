Linux Server Sending Spam Emails? Find the Source & Stop Abuse

By LicenBase Team Published October 20, 2026 Updated October 22, 2026 7 min read

Few operational emergencies disrupt hosting operations as rapidly as an outbound spam explosion. When a compromised email account or malicious PHP script begins pumping tens of thousands of unsolicited messages through your Exim mail transfer agent, your server IP gets blacklisted across global RBLs within hours. Legitimate client business emails fail to reach Outlook, Gmail, or Yahoo, and hosting datacenters issue immediate network abuse notices. This hands-on incident response guide provides the diagnostic commands and systematic methodology to confirm symptoms, inspect Exim mail queues, pinpoint the exact compromised mailbox or PHP mailer script, contain the damage, and restore email deliverability safely.

1. Confirming the Symptoms: RBL Blacklists, Delivery Delays & Queue Spikes

Outbound email abuse often goes unnoticed until customers report that normal business emails are bouncing. Key symptoms of an active spam outbreak include:

  • Exploding Exim Queue Size: The queue jumps from dozens of normal messages to thousands of deferred or frozen records.
  • Non-Delivery Reports (NDRs) Flood: Mailboxes and postmaster aliases are overwhelmed with "Mail Delivery Failed: Returning message to sender" bounces.
  • RBL & DNSBL Blacklisting: Your server IP is flagged on Spamhaus ZEN, Barracuda, or SpamCop, causing recipient mailservers to reject connections with 550 5.7.1 Service unavailable.
  • Port 25 Network Spikes: High outbound network bandwidth on TCP port 25 and high CPU consumption by mail processes, which you can audit using our guide on diagnosing high CPU and suspicious Linux VPS processes.

2. Inspecting the Exim Mail Queue via SSH

Log into your server terminal via SSH as root to inspect the queue without delay:

# View total count of messages currently in the Exim queue
exim -bpc

# Generate an aggregated summary of the queue grouped by domain
exim -bpr | exiqsumm

Sample exiqsumm output highlighting an ongoing spam flood:

Count  Volume  Oldest  Newest  Domain
-----  ------  ------  ------  ------
 8420   42MB    3h      1m     gmail.com
 4110   21MB    3h      2m     yahoo.com
 2350   12MB    3h      1m     hotmail.com
-------------------------------------
14880   75MB    3h      1m     TOTAL

If thousands of messages are queued for consumer webmail domains within a narrow timeframe, an unauthorized sender or compromised script is abusing your server.

3. Examining Queued Message Headers and Message Bodies

To identify the source of the abuse, sample individual messages from the queue using exim -bp:

# List the 10 most recent messages in the queue (captures message IDs)
exim -bp | head -n 20

# View complete email headers for a specific message ID (e.g., 1tQxYz-0001Ab-2C)
exim -Mvh 1tQxYz-0001Ab-2C

# View the message body to inspect the spam payload
exim -Mvb 1tQxYz-0001Ab-2C

When reviewing headers, check two critical indicators:

  • auth_id: If you see auth_id=sales@clientdomain.com, an attacker has stolen the password for that specific email mailbox (often via phishing or credential brute-forcing). Hardening login entry points is detailed in our tutorial on how to secure WHM and cPanel against brute-force attacks.
  • X-PHP-Originating-Script or cwd: If you see X-PHP-Originating-Script: 1004:mailer.php or cwd=/home/clientuser/public_html/wp-content/uploads, a web shell or compromised WordPress plugin was used to inject emails through the local PHP mail() binary.

4. Correlating Exim Mail Logs (/var/log/exim_mainlog)

Correlate your findings by querying Exim\'s transaction log in real time:

# Search for authenticated login senders sending unusually high volumes
grep "auth_id=" /var/log/exim_mainlog | awk '{for(i=1;i<=NF;i++) if($i ~ /auth_id=/) print $i}' | sort | uniq -c | sort -nr | head -n 10

# Search for unauthenticated local user scripts sending mail
grep "cwd=" /var/log/exim_mainlog | awk '{for(i=1;i<=NF;i++) if($i ~ /cwd=/) print $i}' | sort | uniq -c | sort -nr | head -n 10

This immediately identifies the specific cPanel user account, working directory, or mailbox address responsible for the flood.

5. Incident Containment: Suspending Senders & Preserving Evidence

Once the source is identified, execute immediate containment:

  1. If a Mailbox Password Was Stolen: Log into cPanel » Email Accounts » Manage. Change the password immediately and set Outgoing Email Quota to Suspend.
  2. If a PHP Web Shell Was Used: Suspend the cPanel account via WHM or command line (/scripts/suspendacct username "Spam investigation") to freeze all web workers and prevent ongoing outbound connections.
  3. Preserve Forensic Evidence: Before cleaning files, inspect cron jobs (crontab -u username -l), check recently created PHP files (find /home/username/public_html -type f -name "*.php" -mtime -3), and review active user processes (ps -u username -f).

6. Purging Malicious Spam Without Losing Legitimate Mail

Never delete the entire queue. In shared hosting environments, a blanket queue wipe deletes valuable client orders, receipts, and normal correspondence. Instead, target only the spam messages:

# 1. Delete all frozen non-delivery bounces (safe to remove)
exiqgrep -z -i | xargs exim -Mrm

# 2. Delete all queued messages sent by the specific compromised sender address
exiqgrep -i -f "compromised_user@domain.com" | xargs exim -Mrm

# 3. Force delivery attempt for all remaining legitimate queued messages
exim -qf

Frequently asked questions

Common warning signs include an exploding Exim mail queue, thousands of non-delivery report (NDR) bounce-backs filling postmaster mailboxes, high outbound bandwidth on TCP port 25, recipient mail servers returning "550 5.7.1 Service unavailable", and server IP blacklisting on major RBLs like Spamhaus ZEN, Barracuda, or SpamCop.

Compromised scripts utilize PHP mail() or sendmail binaries without SMTP authentication, frequently appearing in message headers as the Apache user, cPanel user, or via X-PHP-Originating-Script. In contrast, stolen email credentials authenticate directly through Dovecot on ports 465 or 587, logging as an authenticated sender (e.g., auth_id=info@domain.com) in /var/log/exim_mainlog.

Never run a blanket command to wipe the entire Exim queue. Instead, target only the compromised sender or frozen delivery failures. Use `exiqgrep -z -i | xargs exim -Mrm` to delete only frozen bounce-backs, or use `exiqgrep -i -f compromised_user@domain.com | xargs exim -Mrm` to delete only messages generated by the identified abusive account.

In WHM Exim Configuration Manager, enable "Query Apache server status for that user" and "Set SMTP Sender: ON". In php.ini, ensure `mail.add_x_header = On`. This instructs the PHP engine to inject an X-PHP-Originating-Script header into every generated email, specifying the exact UID and script path (e.g., /home/user/public_html/wp-content/uploads/mailer.php).

An Imunify360 license actively blocks mailer webshells and phishing scripts before execution using Proactive Defense, while a CloudLinux license enforces strict per-user resource and process quotas with CageFS isolation, preventing compromised accounts from sending mass unauthorized mail.
