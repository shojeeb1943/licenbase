Linux VPS Disk Almost Full? Find Hidden Large Files & Logs

By LicenBase Team Published October 14, 2026 5 min read

Few server crises escalate as rapidly as running out of hard drive space. When a Linux Virtual Private Server (VPS) reaches 99% or 100% disk capacity, the operating system enters an emergency state: MariaDB/MySQL immediately halts to protect database integrity, web servers reject incoming client sessions, mail delivery bounces, and system logging freezes. Even worse, administrators often delete several gigabytes of files, only to find that df -h stubbornly reports zero reclaimed space due to hidden open file descriptors. Recovering disk space safely without deleting critical operating system binaries requires a proven forensic methodology. Here is how to find hidden large files, vacuum runaway logs, and reclaim storage on your Linux VPS.

1. Check Real Disk Usage and Inodes with `df`

The first step is confirming whether you have exhausted physical storage space or filesystem inodes:

# Check partition capacity in human-readable gigabytes
df -h

# Check inode utilization (file count limit)
df -i

If df -h shows available space but df -i shows 100% inode usage, millions of tiny files (such as PHP session files in /var/cpanel/php/sessions/) are choking the filesystem.

2. Scan for Massive Files with `find` and `du`

Quickly locate files larger than 500MB across your root filesystem without traversing mounted network shares:

# Find files exceeding 500 Megabytes
find / -xdev -type f -size +500M -exec ls -lh {} + | awk '{ print $9 ": " $5 }'

# Identify the top 15 largest directories on the root partition
du -ahx / | sort -rh | head -n 15

For an interactive visual terminal explorer, install ncdu (NCurses Disk Usage):

# Install and run ncdu
dnf install -y ncdu || apt install -y ncdu
ncdu -x /

Use arrow keys to browse directories and press d to delete unnecessary archives safely.

3. Vacuum Systemd Journals and Clear Archived Logs

Systemd journal logging can accumulate years of debug entries, silently occupying 5GB to 20GB of disk space in /var/log/journal/:

# Check current journal disk usage
journalctl --disk-usage

# Retain only the last 200MB of logs
journalctl --vacuum-size=200M

# Safely delete rotated compressed gzip logs
rm -f /var/log/*.gz /var/log/*.[0-9]

Never delete active log files directly with rm; instead, truncate them to zero bytes: > /var/log/nginx/error.log.

4. Uncover Ghost Files: Deleted Files Held Open by Active Processes

If you deleted a 10GB log file with rm but df -h does not release the space, an active daemon still has the file descriptor open:

# Identify processes holding deleted unlinked files in memory
lsof +L1

# Look for processes labeled (deleted) with large file sizes
# Restart the responsible service to release the disk blocks:
systemctl restart httpd || systemctl restart nginx

Once the daemon reloads, the Linux kernel immediately frees the allocated blocks back to the free storage pool.

5. Purge Package Manager Caches and Core Dumps

Package managers retain hundreds of cached RPM or DEB installation files:

# RHEL / AlmaLinux / Rocky Linux
dnf clean all

# Ubuntu / Debian
apt clean

# Remove crashed application core dumps in /tmp
rm -f /tmp/core.* /var/tmp/core.*

Frequently asked questions

When disk storage is exhausted, MySQL/MariaDB crashes because it cannot write transactional redo logs, cPanel sessions refuse to save, AutoSSL stops issuing certificates, and SSH key authentication may fail due to unwritable temporary files.

If an active process (such as Nginx, Apache, or MySQL) still holds an open file handle to a deleted file, the operating system marks the directory entry deleted but does not free disk blocks. Run `lsof +L1` to find and restart the locking process.

Systemd journal logs can easily balloon to several gigabytes. You can safely reclaim space immediately by executing `journalctl --vacuum-size=200M` or `journalctl --vacuum-time=7d`.

Common culprits include `/var/log/journal/`, bloated MySQL binary logs in `/var/lib/mysql/`, orphaned account backup archives in `/home/cpeasyapache/` or `/backup/`, and core dump files in `/tmp/`.
