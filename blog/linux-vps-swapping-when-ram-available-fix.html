Why Is Your Linux VPS Swapping When RAM Seems Available?

By LicenBase Team Published October 22, 2026 5 min read

You run free -m on your production Linux VPS and notice something bewildering: your server reports 4 GB of available memory, yet your swap partition is 30% full and disk I/O metrics are spiking. Why would the Linux kernel write memory pages to slow disk swap when fast physical RAM is sitting idle? This counter-intuitive behavior causes immense confusion for hosting providers and system administrators. Understanding the interplay between Anonymous memory, Page Cache, and the vm.swappiness kernel algorithm is key to optimizing your cPanel server for maximum responsiveness.

How the Linux Kernel Values Disk Cache vs Idle RAM

To understand swapping behavior, you must look at how the Linux virtual memory manager categorizes RAM:

  • Anonymous Memory: Memory allocated by executing programs (such as PHP-FPM workers, MySQL query caches, and Nginx buffers) that is not backed by any file on disk. The only way the kernel can free this memory is by writing it to swap.
  • Page Cache & Buffers: Copies of files recently read from or written to disk. Because reading from physical RAM is orders of magnitude faster than reading from NVMe or SSD drives, Linux aggressively fills every byte of otherwise unused RAM with page cache.

When the kernel evaluates system performance, it asks a fundamental question: "Is it better to keep an idle, sleeping PHP thread in RAM that hasn't executed a query in 45 minutes, or should I swap that idle thread to disk and use that RAM to cache active MySQL database files?" By default, the kernel chooses to cache the disk files—resulting in swap usage even when memory appears available.

The Role of the vm.swappiness Kernel Parameter

The kernel's willingness to swap out anonymous process memory in favor of retaining page cache is controlled by vm.swappiness. The scale ranges from 0 to 100 (or up to 200 on newer kernels):

  • Default (60): Standard Linux distributions (Ubuntu, AlmaLinux, Debian, CentOS) ship with swappiness set to 60. This aggressive default is designed for desktop or general-purpose machines, but is far too eager to swap on dynamic web servers.
  • Hosting Recommendation (10): Tells the kernel to aggressively favor reclaiming page cache before touching anonymous process memory, keeping PHP-FPM and MySQL threads in low-latency physical RAM.
  • Minimal (1): Tells the kernel to avoid swapping at all costs, utilizing swap only as an absolute emergency buffer to avoid an OOM Killer panic.

Step 1: Check Swappiness and Identify What is in Swap

Connect to your server via SSH as root and inspect your current swappiness value:

# Check current kernel swappiness setting

cat /proc/sys/vm/swappiness

# Identify which specific processes are occupying swap space

for f in /proc/[0-9]*/status; do awk '/VmSwap/{swap=$2} /Name/{name=$2} /Pid/{pid=$2} END{if(swap>0) print swap, "KB -", name, "(PID " pid ")"}' $f; done | sort -n -r | head -n 15

If you discover that mysqld has 500 MB sitting in swap, your database queries will suffer from intermittent disk latency spikes whenever those swapped pages are referenced.

Step 2: Tune Swappiness for Web Hosting Environments

Lower the swappiness value immediately in runtime memory:

# Apply immediately without a system reboot

sysctl vm.swappiness=10

# Also tune vfs_cache_pressure to prevent retaining stale directory inodes

sysctl vm.vfs_cache_pressure=50

To ensure these settings persist across server reboots, append them to /etc/sysctl.conf:

echo 'vm.swappiness = 10' >> /etc/sysctl.conf

echo 'vm.vfs_cache_pressure = 50' >> /etc/sysctl.conf

Step 3: Safely Purging Existing Swap into RAM

Changing vm.swappiness prevents future premature swapping, but it will not automatically evacuate existing swapped pages back into RAM until those pages are accessed. If your server currently has plenty of free physical memory, you can safely flush swap:

# Verify free RAM exceeds current swap usage before running!

free -m

# Flush swap back into physical RAM and re-enable

swapoff -a && swapon -a

Frequently asked questions

Linux distinguishes between active process memory (anonymous pages) and filesystem cache (page cache). By default, the kernel often decides it is more beneficial for overall system performance to cache frequently accessed disk files in RAM and push idle, sleeping process pages to swap.

The 'vm.swappiness' kernel parameter (ranging from 0 to 200, typically defaulting to 60) represents the kernel's preference balance between reclaiming page cache versus swapping out anonymous process memory. Lower numbers prioritize keeping process memory in physical RAM.

For web hosting servers running cPanel, MySQL, and PHP-FPM, setting vm.swappiness to 10 (or 1 on high-RAM servers) is optimal. This prevents the server from swapping out idle database threads while still preserving swap as an emergency safety valve.

If you have enough free RAM to hold the swapped data, run 'swapoff -a && swapon -a' as root. The kernel will read all swapped pages from disk back into physical RAM and re-enable swap.
