Critical PHP RCE (CVE-2026-109618): Hosting Server Fix Guide

By LicenBase Team Published October 22, 2026 12 min read

On October 21, 2026, the PHP development team published an emergency global security advisory announcing two critical remote code execution (RCE) vulnerabilities: CVE-2026-109618 and CVE-2026-109619. Both vulnerabilities affect all standard web deployment models - including PHP-FPM, Apache mod_php, FastCGI, FrankenPHP, and LiteSpeed LSPHP. Because these memory management flaws reside inside core request lifecycle routines, unauthenticated remote attackers can craft specialized HTTP requests that trigger heap corruption and achieve arbitrary code execution with the privileges of the web server worker. This operational incident response runbook provides system administrators, hosting companies, and DevOps engineers with the necessary technical procedures to audit, patch, and verify every PHP runtime across cPanel, Plesk, DirectAdmin, LiteSpeed, standalone Linux distributions, and container clusters.

1. Emergency Incident Response Checklist

Immediate Administrator Action Items

  • Do not rely on single CLI checks: Running php -v tests only the shell binary, not the web server worker pools handling live traffic.
  • Prioritize internet-facing multi-tenant nodes: Patch public shared hosting, agency servers, and SaaS application gateways before internal staging instances.
  • Update package managers: Execute platform-specific updates for EasyApache 4, Plesk PHP handlers, CustomBuild, or distribution repositories.
  • Force service recycles: Restart every individual PHP-FPM pool, kill lingering lsphp processes, and gracefully reload Apache/NGINX.
  • Audit runtime versions: Verify that active web requests report fixed versions (PHP 8.2.35+, 8.3.36+, 8.4.27+, or vendor security backports).

2. Technical Breakdown: CVE-2026-109618 and CVE-2026-109619

To safely evaluate the blast radius of these vulnerabilities, administrators must understand the underlying memory lifecycle failures:

  • CVE-2026-109618 (Out-of-Memory Partial Initialization): During the handling of multipart request payloads or deeply nested array allocations, memory allocation exhaustion can trigger early request termination. In unpatched releases, the exception handling cleanup routines assume that internal request data structures were fully initialized. When the cleanup routine executes against partially initialized memory pointers, it attempts to release unallocated or misaligned addresses, triggering an exploitable heap corruption vulnerability.
  • CVE-2026-109619 (Stale Request State Use-After-Free): When persistent worker processes (such as PHP-FPM or LiteSpeed worker daemons) handle sequential HTTP requests over kept-alive FastCGI sockets, request shutdown routines failed to clear reference handles for specific internal telemetry and buffer structures. Consequently, stale state pointers survived deallocation and were re-referenced during the initialization of a subsequent HTTP request, resulting in a use-after-free condition.

Because both vulnerabilities can be triggered by standard HTTP request sequences without requiring administrative authentication, internet-facing servers must be patched immediately.

3. Affected Versions and Fixed Target Releases

The upstream PHP project released synchronized security updates across all currently supported development branches. Compare your installed versions against the verified target releases:

PHP Branch Upstream Status Vulnerable Releases Fixed Upstream Version Vendor Backport Guidance
PHP 8.5 Active Support < 8.5.12 8.5.12 Official upstream binaries
PHP 8.4 Active Support < 8.4.27 8.4.27 Official upstream & distribution backports
PHP 8.3 Active Support < 8.3.36 8.3.36 cPanel EA4, Plesk, Debian/Ubuntu USN
PHP 8.2 Security Fixes Only < 8.2.35 8.2.35 cPanel EA4, RHEL/Alma, Ubuntu USN-8948-1
PHP 8.1 & Earlier End of Life (EOL) All releases No upstream patch Requires CloudLinux HardenedPHP or upgrade

Crucial Note on Backports: Enterprise Linux distributions (such as Ubuntu LTS, Debian, Red Hat Enterprise Linux, AlmaLinux, and Rocky Linux) backport security fixes into existing minor versions without bumping the upstream version string. On these systems, verify the package release changelog rather than relying exclusively on the upstream version number.

4. Identifying Every Active PHP Runtime on Your Server

Modern hosting servers rarely run a single PHP binary. To ensure complete remediation, you must identify every runtime environment handling requests on the machine:

  • MultiPHP Runtimes: Control panels allow different client accounts or virtual hosts to run separate PHP versions simultaneously (e.g., domain A on PHP 8.2 and domain B on PHP 8.4).
  • PHP-FPM Worker Pools: Each domain may utilize its own PHP-FPM pool socket located under /var/run/php-fpm/ or /opt/cpanel/ea-php*/root/usr/var/run/php-fpm/.
  • LiteSpeed External Applications: LiteSpeed Web Server and OpenLiteSpeed run separate LSPHP binaries (such as /usr/local/lsws/lsphp83/bin/lsphp).
  • Containerized Runtimes: Docker or Kubernetes pods running NGINX and PHP-FPM carry their own internal base images, which are completely untouched by host operating system updates.

Run the following command as root to discover all active PHP processes currently running in memory:

# Identify all running PHP master and worker processes
ps aux | grep -E "php-fpm|lsphp|php" | grep -v grep

5. cPanel & WHM: EasyApache 4 Remediation Runbook

On cPanel & WHM servers, website runtimes are managed via EasyApache 4 (EA4). Note that executing a standard /scripts/upcp updates the cPanel core software, but website runtimes must be patched through EA4 RPM packages.

Follow these steps from the root SSH terminal:

# 1. Clean package metadata caches
yum clean all || dnf clean all

# 2. Update all installed EasyApache 4 PHP packages
yum update "ea-php*" -y || dnf update "ea-php*" -y

# 3. Restart all active cPanel PHP-FPM service daemons
/scripts/restartsrv_apache_php_fpm

# 4. Gracefully reload the Apache web server
/scripts/restartsrv_httpd --graceful

To verify the installed versions of each EA4 PHP package, query the RPM database:

# Inspect installed EA4 PHP versions
rpm -qa | grep -E "ea-php8[2-5]-php-cli"

Ensure that all hosted accounts in WHM » MultiPHP Manager reflect the updated PHP versions. For administrators managing fleets of cPanel servers, an authentic cPanel & WHM license provides direct access to official mirrors and automated security updates.

6. Plesk Hosting Servers: Multi-Version Handler Updates

Plesk manages multiple PHP runtimes independently of the operating system's base PHP package. To update all Plesk-managed PHP handlers:

# 1. Update Plesk components and all Plesk PHP handlers via CLI
plesk installer update --recommends

# 2. List all registered PHP handlers and verify their status
plesk bin php_handler --list

# 3. Restart all Plesk PHP-FPM service daemons
systemctl restart "plesk-php*-fpm"

# 4. Gracefully restart the web server
systemctl reload nginx && systemctl reload apache2 || systemctl reload httpd

Verify individual handler binaries directly from the command line:

# Check the version of Plesk PHP 8.3
/opt/plesk/php/8.3/bin/php -v

7. DirectAdmin and CustomBuild Environments

DirectAdmin compiles or installs pre-compiled binary PHP packages using the CustomBuild 2.0 utility. To update all active PHP versions:

# 1. Navigate to CustomBuild directory
cd /usr/local/directadmin/custombuild

# 2. Update build definitions
./build update

# 3. Rebuild and update all configured PHP versions
./build php_versions

# 4. Rewrite web server configurations and restart services
./build rewrite_confs

Verify that /usr/local/php*/bin/php -v reports the fixed versions across all configured PHP slots (e.g., php1_release, php2_release).

8. CyberPanel, OpenLiteSpeed and LiteSpeed Enterprise

LiteSpeed Web Server Enterprise and OpenLiteSpeed communicate with PHP through the high-performance LSPHP binary interface. Upgrading the web server binary or holding a LiteSpeed license does not automatically patch LSPHP packages.

Apply updates depending on your operating system:

# On RHEL / AlmaLinux / CloudLinux / Rocky Linux:
dnf update "ls-php*" -y || yum update "ls-php*" -y

# On Ubuntu / Debian:
apt update && apt --only-upgrade install "ls-php*" -y

# IMPORTANT: Force LiteSpeed to terminate cached LSPHP worker processes
killall -9 lsphp

# Restart LiteSpeed Web Server
/usr/local/lsws/bin/lswsctrl restart

9. Standalone Ubuntu and Debian Servers (No Control Panel)

For standalone virtual servers running NGINX or Apache with Ondřej Surý's PPA or official distribution mirrors, refer to Ubuntu Security Notice USN-8948-1:

# 1. Update package indices
sudo apt update

# 2. Upgrade all installed PHP packages
sudo apt --only-upgrade install "php8.*-fpm" "php8.*-cli" "php8.*-common" "libapache2-mod-php8.*" -y

# 3. Restart PHP-FPM service daemons
sudo systemctl restart "php8.*-fpm"

# 4. Reload web servers
sudo systemctl reload nginx && sudo systemctl reload apache2

10. AlmaLinux, Rocky Linux, CloudLinux and RHEL-Family Servers

On standalone enterprise Linux machines using DNF module streams or Remi's RPM repository:

# 1. Check for available PHP security errata
dnf check-update --security

# 2. Apply security updates for PHP packages
dnf upgrade --security "*php*" -y

# 3. Restart system PHP-FPM
systemctl restart php-fpm

# 4. Reload web server
systemctl reload httpd || systemctl reload nginx

CloudLinux HardenedPHP Support: For shared hosting providers running legacy workloads (such as PHP 7.4 or 8.0), a CloudLinux license provides HardenedPHP protection, which backports fixes for critical memory management vulnerabilities directly into end-of-life PHP runtimes.

11. Docker, Kubernetes and Container Deployments

Updating the container host's operating system does not patch PHP runtimes executing inside containers. Container workloads must be updated via image rebuilds:

  1. Update Dockerfile Base Images: Ensure all base images point to the latest official patch release (e.g., FROM php:8.3.36-fpm-alpine).
  2. Rebuild Container Images: Recompile application containers with docker compose build --no-cache.
  3. Redeploy Workloads: Roll out updated pods across your Kubernetes cluster or container service: 
    # Rolling restart of PHP workloads in Kubernetes
kubectl rollout restart deployment/php-fpm-app
  4. Purge Vulnerable Images: Remove outdated container images from local registries to prevent accidental redeployment.

12. Post-Patch Verification Procedures

Do not declare a server secure until you verify that live web requests execute the patched binary. Follow this non-destructive verification procedure:

  1. Create a temporary, randomly named verification file in a test virtual host's document root: 
    # Create a secure single-purpose version checker
echo '<?php header("Content-Type: text/plain"); echo phpversion(); ?>' > /home/testuser/public_html/sec_ver_check.php
  2. Query the endpoint locally via curl to inspect the live web runtime version: 
    # Query the web-delivered version
curl -k https://testdomain.com/sec_ver_check.php

# Expected output: 8.3.36 (or verified distribution backport string)
  3. Immediately remove the verification file to prevent leaking configuration details: 
    rm -f /home/testuser/public_html/sec_ver_check.php

13. Temporary Containment When Patching Is Delayed

If legacy application dependencies prevent immediate package upgrades, implement temporary containment controls:

  • Restrict Network Exposure: Place administrative dashboards, internal tools, and staging environments behind IP whitelists or a private VPN.
  • Deploy Web Application Firewalls: Deploy an Imunify360 license to leverage its multi-layer ModSecurity WAF rules, real-time PHP blamer, and proactive defense system. While the PHP project notes that a WAF is not a substitute for binary patching, Imunify360 significantly reduces automated exploit scanning.
  • Account Isolation: Enforce CageFS virtualized file system isolation through CloudLinux OS so that if a single site is compromised, the attacker cannot read neighboring virtual hosts or access the core system.

14. Investigating a Suspected Compromise

If you suspect an unpatched server was targeted prior to remediation, conduct forensic log analysis before wiping or restarting systems:

  • Inspect Web Access Logs: Search for abnormal POST requests, high volumes of chunked transfer-encoding requests, or out-of-memory errors in /var/log/httpd/error_log, /var/log/nginx/error.log, and per-user PHP-FPM error logs.
  • Audit Active Connections and Processes: Check for anomalous outbound network sockets or unauthorized background worker processes using our guide on diagnosing high CPU and suspicious Linux VPS processes.
  • Check Persistence Mechanisms: Review crontabs (/etc/crontab, /var/spool/cron/), systemd unit files, and recently modified PHP files in web roots: 
    # Find PHP files modified in the last 48 hours
find /home/*/public_html -type f -name "*.php" -mtime -2
  • Review Authentication Logs: Inspect /var/log/secure or /var/log/auth.log to identify unauthorized root logins or privilege escalation attempts, following our guide on securing WHM and cPanel against brute-force attacks.
