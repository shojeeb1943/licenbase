The Architecture of a Virtualizor Cloud Cluster

Virtualizor operates on an efficient Master/Slave clustering architecture designed to manage dozens of bare-metal hypervisors from a single centralized pane of glass:

  • Virtualizor Master Node: Serves the main administrative dashboard, user client portal, IP address pool management, and REST API endpoints. It connects directly to billing platforms like WHMCS for automated provisioning. The Master node can also host virtual machines itself.
  • Virtualizor Slave Nodes: Dedicated bare-metal hypervisor servers located in any global datacenter. Slave nodes execute VM virtualization commands, monitor hardware resource usage, and report metrics back to the Master node.

Deploying through an automated Virtualizor license unlocks unlimited VPS creation on every licensed node without per-core or per-VM penalties.

Node Capacity Planning: Calculating KVM Density

To run a profitable VPS business, you must calculate exactly how many virtual machines a single bare-metal node can safely host without sacrificing guest performance. Here is the sizing methodology used by top infrastructure architects:

1. Physical RAM: Strict 1:1 Allocation

Unlike CPU cores, physical RAM should **never** be overcommitted on KVM nodes. If guest VMs request more RAM than physically exists, the hypervisor's swap partitions thrash, bringing disk I/O to a standstill.

On a bare-metal server with 128GB RAM: reserve 8GB for the hypervisor host OS (AlmaLinux 9 + Virtualizor). The remaining 120GB can be divided into guest VPS plans (e.g., 60 VPS instances with 2GB RAM each, or 30 VPS instances with 4GB RAM each).

2. CPU Overcommitment Ratio (2:1 to 3:1)

Most customer VPS instances sit idle between 85% and 95% of the time, experiencing only periodic bursts during page loads or cron runs. On modern AMD EPYC or Intel Xeon processors, a **2:1 to 3:1 vCPU-to-physical-thread ratio** is safe and industry standard.

On a 16-Core / 32-Thread AMD EPYC server, a 2.5:1 overcommit ratio gives you **80 virtual CPU cores** to distribute across your guest VMs.

3. Storage Throughput: NVMe RAID-10

Always configure storage pools using enterprise NVMe SSDs in hardware RAID-10 or ZFS mirror pools. Standard SATA SSDs will bottle up under concurrent write operations when multiple guest OS instances run package updates simultaneously.
