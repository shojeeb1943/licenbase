VPS CPU Usage at 100%? Linux Commands to Find and Fix the Process

By LicenBase Team Published October 12, 2026 5 min read

Seeing your Linux VPS spike to 100% CPU utilization is one of the most urgent operational emergencies a system administrator can face. When compute resources are pinned at maximum capacity, websites load sluggishly or return 504 Gateway Timeout errors, SSH sessions become laggy and unresponsive, and cron tasks begin queuing indefinitely. Pinpointing the exact runaway script, rogue database query, or unauthorized cryptocurrency miner causing the spike requires a structured command-line troubleshooting approach. This hands-on guide details the essential terminal tools—including top, htop, ps, pidstat, and vmstat—to identify the offending process and restore normal server operations.

Step 1: Real-Time Process Inspection with top and htop

The standard tool pre-installed on virtually all Linux distributions is top. Connect to your VPS via SSH and run:

top -c

The -c flag displays the full command-line arguments and paths rather than truncated process names. While inside top, press Shift + P to instantly sort the process list by CPU percentage in descending order.

If installed, htop provides an even more intuitive, color-coded visual overview with interactive filtering:

# Install htop on AlmaLinux / Rocky Linux / RHEL
dnf install epel-release -y && dnf install htop -y

# Launch htop
htop

Step 2: Pinpointing the Exact Process with ps aux

When you need a clean, scriptable snapshot of the top five CPU-consuming processes on your server, use ps sorted by resource utilization:

ps aux --sort=-%cpu | head -n 6

This command outputs the user owner, Process ID (PID), percentage of CPU and memory consumed, execution time, and the exact executable path. Common culprits include:

  • php-fpm or lsphp processes: Typically indicates a runaway WordPress plugin loop, unoptimized database query, or brute-force POST attack hitting xmlrpc.php or wp-login.php.
  • mysqld / mariadb: Indicates missing table indexes, runaway un-indexed JOIN operations, or table crashes causing full table scans.
  • Rogue Cron Jobs or Backup Tasks: Uncompressed tarball operations or backup routines overlapping with peak daytime web traffic hours.
  • Suspicious Hidden Binaries: Random-character executables in /tmp or /dev/shm indicating cryptocurrency mining malware.

Step 3: Checking I/O Wait (%wa) vs. Pure Compute

A common pitfall is assuming high load averages always mean heavy CPU computation. Inspect the CPU summary line at the top of top or run vmstat 1 5:

vmstat 1 5

Look at the wa (Wait) column under the CPU header. If %wa is above 15-20%, your CPU cores are not actually overloaded with calculations; they are stalled waiting for your VPS storage disk to read or write data. If this occurs, identify disk hogs using iotop -oPa.

Step 4: Using pidstat to Track Process CPU Spikes Over Time

If a rogue script spikes periodically and disappears before you can catch it in top, use pidstat from the sysstat package to record interval sampling:

# Sample CPU activity every 2 seconds for 5 iterations
pidstat -u 2 5

# Sample I/O activity per process to detect heavy disk writers
pidstat -d 2 5

This reveals the historical behavior of short-lived worker threads that spike compute cycles during incoming web requests.

Step 5: Gracefully Terminating or Force Killing the Rogue Process

Once you have identified the offending Process ID (PID), terminate it safely:

# Step 1: Attempt graceful shutdown (SIGTERM)
kill -15 <PID>

# Step 2: If the process fails to terminate after 10 seconds, force kill (SIGKILL)
kill -9 <PID>

# Step 3: Kill all processes belonging to an abusive user
pkill -u abusiveusername -9

Always attempt kill -15 first to give database engines and web servers an opportunity to release shared memory locks and prevent table corruption.

Frequently asked questions

Running `top` or `htop` in your terminal gives an instant real-time view. In `top`, press `P` (capital P) to sort processes by CPU utilization percentage. In `htop`, press `F6` and choose `PERCENT_CPU`.

`kill -15` (SIGTERM) sends a graceful termination request, allowing the application to save state, close database connections, and flush buffers cleanly. `kill -9` (SIGKILL) forcefully terminates the process immediately at the kernel level, which should be used only if the process is unresponsive to SIGTERM.

Check the `%wa` (I/O wait) metric in `top` or `vmstat 1`. If your VPS storage disk is saturated with heavy database read/writes or memory swapping, the CPU cores spend majority cycles waiting for disk I/O, driving the load average abnormally high.
