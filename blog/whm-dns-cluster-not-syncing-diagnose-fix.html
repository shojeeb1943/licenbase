WHM DNS Cluster Not Syncing: Diagnose & Fix Zone Errors

By LicenBase Team Published October 22, 2026 7 min read

A reliable DNS cluster is the foundation of high-availability web hosting. When you configure cPanel & WHM in a distributed DNS cluster across independent cPanel DNSOnly nodes, domain records, mail exchangers (MX), and SPF/DKIM records are automatically pushed to authoritative nameservers in real time. However, when zone synchronization breaks, websites experience intermittent resolution outages, newly added domains fail to resolve, and system administrators see cryptic dnsadmin timeout warnings in WHM. This comprehensive guide walks through the architecture of WHM DNS clustering, isolates root failure causes, and provides step-by-step diagnostic workflows to restore automated zone synchronization across your infrastructure.

How WHM DNS Clustering Architecture Operates

In a standard cPanel & WHM deployment, the local web server runs an authoritative nameserver daemon—either BIND (named) or PowerDNS (pdns). In a clustered environment, WHM decouples DNS resolution from the web server by routing all zone updates through the internal dnsadmin daemon to one or more remote nameservers running cPanel DNSOnly.

When an administrator or customer creates an account, modifies an A record in cPanel Zone Editor, or issues an AutoSSL certificate, the local dnsadmin service dispatches an authenticated HTTPS call over TCP port 2087 to the remote WHM API endpoint. The remote server receives the raw zone payload, writes it to /var/named/example.com.db, increments the serial number, and executes an internal zone reload command (such as rndc reload). When synchronization fails, the breakdown typically occurs at one of three checkpoints: network connectivity, API token authorization, or zone file syntax corruption.

Common Symptoms and Error Signatures

DNS cluster sync failures manifest through distinct administrative and end-user symptoms:

  • WHM Cluster Configuration Warning: Under Home » DNS Functions » DNS Cluster, the remote server displays a red status icon or throws Cluster connection failed: Connection refused or timed out.
  • Stale Records on Remote Nameservers: Querying the local server via dig @localhost example.com returns the newly updated IP, while querying the public authoritative nameserver via dig @ns1.yourhost.com example.com returns the old IP address.
  • Account Creation Freezes: Creating a new cPanel user in WHM or through automated provisioning via WHMCS billing hangs for 60 to 120 seconds while WHM waits for a timed-out remote DNS socket to abort.
  • Mail Delivery Rejections: Inbound mail servers bounce messages with 550 Relaying denied or DNS lookup failure because MX records failed to propagate to the cluster nodes.

Step 1: Verify Port 2087 Network Connectivity and Firewall Rules

The primary cPanel server must be able to initiate outbound TCP connections to port 2087 on each remote DNSOnly node, and each DNSOnly node must permit inbound traffic on port 2087 from the master server's public IP address. Security firewalls like ConfigServer Security & Firewall (CSF) or native nftables/iptables frequently block this traffic after an IP change or software update.

Log into your primary WHM server via SSH as root and test connectivity using curl or nc (netcat):

# Replace 198.51.100.20 with your remote DNSOnly server IP

curl -k -v --connect-timeout 10 https://198.51.100.20:2087/

If the connection hangs or returns Connection timed out, port 2087 is blocked. Log into the remote DNSOnly node and ensure the master server IP is whitelisted:

# Whitelist master server IP in CSF on the remote nameserver

csf -a 203.0.113.10 "Master cPanel WHM Server"

csf -r

# If using native firewalld:

firewall-cmd --permanent --zone=public --add-rich-rule='rule family="ipv4" source address="203.0.113.10" port port="2087" protocol="tcp" accept'

firewall-cmd --reload

Step 2: Inspect and Regenerate WHM API Tokens

Modern cPanel & WHM versions rely on API Tokens rather than legacy remote access keys (.accesshash). If an administrator revokes a token, if an expiration date passes, or if root passwords were reset without updating cluster trust credentials, synchronization halts immediately.

To inspect active cluster configuration files on your master server, check the cluster metadata directory:

ls -la /var/cpanel/cluster/

cat /var/cpanel/cluster/root/config

If you suspect an authentication failure, reconnect the cluster node cleanly through WHM:

  1. Log into the remote DNSOnly node WHM interface (https://ns1.yourhost.com:2087).
  2. Navigate to Home » Development » Manage API Tokens.
  3. Generate a new token with full DNS Clustering permissions (specifically dns-clustering, zone-edit, and nameserver-config).
  4. Log into your master cPanel server WHM interface.
  5. Navigate to Home » DNS Functions » DNS Cluster, click Edit on the affected server, and paste the newly generated API token.
  6. Set the DNS role to Write-Only (recommended for web hosts) or Synchronize Changes, then click Save.

Step 3: Force Cluster Synchronization via Command-Line Tools

When the web interface fails to flush pending zone updates or when dozens of zones are out of sync, running cPanel's native command-line cluster scripts provides detailed, real-time debugging output.

Execute the master synchronization utility on your primary server:

# Synchronize every hosted zone to all active cluster nodes

/scripts/dnscluster syncall

# If a specific domain is reporting stale DNS records:

/scripts/dnscluster synczone example.com

Review the command output carefully. If the script reports Skipping sync for example.com: zone file syntax error, the cluster refused to broadcast the record because the zone file is corrupted.

Step 4: Audit and Repair Corrupted BIND Zone Files

A single malformed DNS record (such as an unclosed quote in a TXT/DKIM record, a missing trailing dot on a CNAME, or an illegal TTL value) will cause named-checkzone to fail. When a zone is syntactically invalid, WHM halts cluster broadcasting for that domain to prevent crashing the remote nameserver daemon.

Validate the local zone file syntax using native BIND diagnostic utilities:

# Verify syntax for a problematic domain

named-checkzone example.com /var/named/example.com.db

If the check outputs errors such as has no address records (A or AAAA) or bad zone transfer format, edit the zone file manually in /var/named/example.com.db or fix it inside WHM Edit DNS Zone. Once corrected, rebuild the DNS configuration and increment the serial number:

# Rebuild DNS configuration and re-index zone templates

/scripts/rebuilddnsconfig

# Restart named / PowerDNS service

/scripts/restartsrv_named

Best Practices for High-Availability DNS Clustering

To avoid cluster degradation in enterprise environments, adhere to these architectural recommendations:

  • Deploy Geographically Isolated DNSOnly Nodes: Run at least two cPanel DNSOnly instances hosted on separate networks, data centers, and upstream transit providers. cPanel DNSOnly requires minimal resources (1 vCPU, 1 GB RAM) and does not require a paid cPanel license.
  • Use Write-Only Configuration on Master Servers: If you operate multiple web servers, configure all web servers in Write-Only mode pointing to your DNSOnly nodes, and configure DNSOnly nodes in Standalone mode. Never configure web servers to synchronize bidirectionally with each other, as circular replication loops can corrupt zone serial numbers.
  • Automate Service Monitoring: Add port 2087 and port 53 (UDP/TCP) health checks to your external monitoring stack (such as UptimeRobot or Prometheus) to detect network partitions before customers notice propagation delays.
