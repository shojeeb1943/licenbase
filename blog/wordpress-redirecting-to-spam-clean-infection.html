WordPress Redirecting to Spam Websites? How to Clean Infection

By LicenBase Team Published October 20, 2026 6 min read

Few malware infections inflict faster commercial damage on a web business than a WordPress spam redirect. Visitors clicking your search results from Google, Bing, or social media find themselves hijacked to fraudulent casino portals, tech-support scam pages, or phishing landing pages. To make matters worse, site administrators often remain unaware of the infection for days because the malware uses conditional cloaking—intentionally sparing visitors who type the URL directly or who have an active administrator cookie. In this practical troubleshooting guide, we demonstrate how to detect cloaked redirects, locate malicious JavaScript across your database and theme files, cleanse .htaccess rewrite injections, and restore your domain reputation.

1. Understanding Conditional Cloaking in Redirect Malware

Modern redirect malware is engineered to maximize ad impressions while evading detection by the site owner. Attackers accomplish this by evaluating incoming HTTP request headers:

  • Referer Filtering: The malware triggers only if the HTTP_REFERER contains search engines such as google.com, bing.com, or yahoo.com.
  • User-Agent Targeting: The redirect targets mobile operating systems (iOS and Android) where visitors are less likely to inspect URLs or developer consoles.
  • Cookie Suppression: If the visitor has a WordPress session cookie (such as wordpress_logged_in_*), the redirect script suppresses itself completely, allowing the site owner to browse the WordPress dashboard normally without noticing anything amiss.

2. Testing and Replicating the Redirect with cURL

To confirm the infection without risking client devices, emulate a mobile search visitor via terminal using curl:

# Test with Google referrer and mobile user-agent
curl -I -s -A "Mozilla/5.0 (iPhone; CPU iPhone OS 16_5 like Mac OS X)" \
  -e "https://www.google.com/" https://example.com/

Sample infected output:

HTTP/2 302
date: Tue, 20 Oct 2026 07:15:22 GMT
location: https://malicious-traffic-portal.example/redirect.php
server: nginx

If the response returns a 301 Moved Permanently or 302 Found status pointing to an external spam URL, conditional server-level redirect rules are active.

3. Inspecting and Cleansing .htaccess and Nginx Configurations

The most common hiding spot for server-level redirects is the root .htaccess file. Attackers inject RewriteRules that check HTTP_USER_AGENT and HTTP_REFERER before regular WordPress rules:

# Inspect the top and bottom of .htaccess
cat public_html/.htaccess

Sample malicious injection:

RewriteCond %{HTTP_REFERER} (google|bing|yahoo) [NC]
RewriteCond %{HTTP_USER_AGENT} (android|iphone|mobile) [NC]
RewriteRule ^(.*)$ https://spam-gateway-node.example/$1 [R=302,L]

To fix this, reset .htaccess to the default clean WordPress rules:

# Backup the infected file for forensic records
cp public_html/.htaccess public_html/.htaccess.bak

# Deploy clean WordPress rules
cat << 'EOF' > public_html/.htaccess
# BEGIN WordPress
RewriteEngine On
RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
RewriteBase /
RewriteRule ^index\.php$ - [L]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /index.php [L]
# END WordPress
EOF

Set file permissions to 644 or temporarily 444 to prevent immediate reinfection while you inspect the database.

4. Scrubbing Malicious JavaScript from the WordPress Database

When the redirect is implemented in JavaScript rather than HTTP headers, the browser downloads the webpage normally, but an inline script executes window.location.href. These scripts are typically injected into the wp_options table or appended to posts in wp_posts.

Connect to MySQL or open phpMyAdmin to inspect the options table:

# Verify siteurl and home point strictly to your verified domain
SELECT option_name, option_value FROM wp_options WHERE option_name IN ('siteurl', 'home');

# Search for malicious script tags in options
SELECT option_id, option_name FROM wp_options WHERE option_value LIKE '%<script%eval%';

Next, search across published posts for injected external script loaders:

SELECT ID, post_title FROM wp_posts WHERE post_content LIKE '%<script%src=%' LIMIT 10;

Delete unauthorized option entries and remove injected script tags from post content. Clear all server-side caches (such as LiteSpeed Cache or Redis object caches) immediately after database cleaning.

5. Auditing Theme Files and Injected Headers

Attackers frequently append their loader scripts directly to the active theme's header.php or functions.php file:

# Inspect the top of the active theme header
head -n 25 wp-content/themes/activetheme/header.php

# Search for obfuscated char codes or eval functions
grep -rnEi "(fromCharCode|base64_decode|eval\()" wp-content/themes/

If malicious functions are found, replace the theme files with a clean, freshly downloaded archive from the official theme repository or author backup.

Frequently asked questions

Attackers write conditional malware designed specifically to bypass the site owner. The malicious code checks the HTTP Referer header for search engines (like google.com or bing.com) and checks the User-Agent header for mobile browsers before triggering the redirect. Typing the URL directly or logging in as administrator bypasses the redirect.

Redirect malware is most frequently found in: (1) root `.htaccess` file via malicious RewriteRules, (2) the `wp_options` database table under `siteurl`, `home`, or rogue autoloaded options, (3) active theme `header.php` or `functions.php` files as injected `<script>` tags, and (4) malicious caching plugins dropped into `wp-content/plugins`.

Use curl with simulated Google referrer and mobile user-agent headers: `curl -I -A "Mozilla/5.0 (iPhone; CPU iPhone OS 14_0 like Mac OS X)" -e "https://www.google.com" https://example.com`.
